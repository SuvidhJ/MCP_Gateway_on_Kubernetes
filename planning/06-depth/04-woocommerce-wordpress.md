# 06·04 — WooCommerce and WordPress, From the Source

Written 2026-10-09 from source at the current releases: **WooCommerce 11.2.0** (released 2026-10-07; requires WP 7.0,
PHP 7.4 minimum), **WordPress 7.1.3**, the official `wordpress` Docker image (`docker-library/wordpress`, tags
`7.1.3-php8.4-apache`, CLI `cli-2.12.0-php8.4`). Recommended runtime per woocommerce.com: PHP 8.3+, **MySQL 8.0+ or
MariaDB 10.6+**, WP memory ≥ 256 MB, HTTPS. File references are WooCommerce `plugins/woocommerce/...` at tag 11.2.0
unless noted.

Purpose: our WooCommerce MCP server (5 tools), the store bootstrap Job, and the storefront DoD (COD checkout) all
depend on these exact behaviours. The reviewers are ex-Automattic WooCommerce people, so this layer is where
precision shows.

## 1. How our MCP server authenticates to WooCommerce (code-verified)

### 1.1 Two credential types WordPress/WooCommerce accept

| | WooCommerce REST API key (`ck_…`/`cs_…`) | WordPress Application Password |
|---|---|---|
| Created by | WC admin UI or the `/wc-auth/v1/authorize` flow (`WC_Auth::create_keys`); **no WP-CLI command** | `wp user application-password create <user> <name> --porcelain` (WP-CLI built-in) |
| Stored as | `wp_woocommerce_api_keys.consumer_key = hash_hmac('sha256', ck, 'wc-api')`; **`consumer_secret` stored in plaintext**; `truncated_key` = last 7 chars | hashed in user meta (WP 6.8+ uses BLAKE2b via sodium) |
| Scope | `permissions` = `read` / `write` / `read_write`, enforced **per HTTP method** (`check_permissions`: GET/HEAD need read; POST/PUT/PATCH/DELETE need write). Since 11.1.0 `reject_out_of_scope_route` refuses the key outside WooCommerce namespaces | full capabilities of the user, all REST namespaces |
| Plus | the owning **user's capabilities** still apply (controller permission callbacks) | same |
| Over plain HTTP | Basic auth only `if ( is_ssl() )`, else OAuth 1.0a signed against `get_home_url()` | only if `wp_is_application_passwords_supported()` = `is_ssl() \|\| 'local' === wp_get_environment_type()` |
| Audit trail | `last_access` updated | user meta `last_used` |

**Choice input:** a WC key with `read_write`, owned by a **dedicated low-capability user**, is the tightest. The key is
limited to WC routes and by HTTP method, and the user's role limits it further (§3).

### 1.2 The `is_ssl()` hurdle and why in-cluster Basic auth works

- `wp-config-docker.php` (official image) contains:
  ```php
  if (isset($_SERVER['HTTP_X_FORWARDED_PROTO']) && strpos($_SERVER['HTTP_X_FORWARDED_PROTO'], 'https') !== false) {
  	$_SERVER['HTTPS'] = 'on';
  }
  ```
  So an in-cluster call to `http://wordpress.<ns>.svc/` carrying `X-Forwarded-Proto: https` makes `is_ssl()` true, and WC
  takes the **Basic auth** path: `PHP_AUTH_USER`=ck, `PHP_AUTH_PW`=cs, `hash_equals` on the secret.
- The image's Apache config also installs `RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]` and mod_php sets
  `PHP_AUTH_USER/PW`, so the header reaches PHP.
- WC Basic auth also accepts `?consumer_key=&consumer_secret=` query params. **Never use them** (they'd show up in access logs).
- **Security caveat:** the template trusts `X-Forwarded-Proto` from **any** caller. Externally, Traefik rewrites
  `X-Forwarded-*` from untrusted clients to the real scheme (06·05), so outside callers can't fake it through the
  Ingress. Inside the cluster, NetworkPolicy must limit who can reach WordPress's Service directly: only the MCP server
  and the Ingress controller.
- The OAuth 1.0a alternative signs `rawurlencode(get_home_url(null, $request_path, is_ssl() ? 'https' : 'http'))`,
  i.e. the **public** URL. It also has a ±15 min timestamp window and nonces stored per key in the DB. That's more
  moving parts for no gain in-cluster.

### 1.3 Creating the key non-interactively (bootstrap)

`WC_Auth::create_keys` does `ck_ . wc_rand_hash()` (40 hex from `random_bytes(20)`) and inserts the HMAC hash. A
bootstrap `wp eval` can do the same with **values supplied from a Kubernetes Secret** (generated by Helm on install):

```php
// wp eval-file create-key.php  (env: MCP_WC_CK, MCP_WC_CS, MCP_WC_USER)
global $wpdb;
$ck = getenv('MCP_WC_CK'); $cs = getenv('MCP_WC_CS');
$user = get_user_by('login', getenv('MCP_WC_USER'));
$hash = hash_hmac('sha256', $ck, 'wc-api');
$table = $wpdb->prefix . 'woocommerce_api_keys';
if (!$wpdb->get_var($wpdb->prepare("SELECT key_id FROM $table WHERE consumer_key=%s", $hash))) {
  $wpdb->insert($table, ['user_id'=>$user->ID, 'description'=>'urumi-mcp (bootstrap)', 'permissions'=>'read_write',
    'consumer_key'=>$hash, 'consumer_secret'=>$cs, 'truncated_key'=>substr($ck,-7)]);
}
```

Idempotent (re-run safe). The plaintext secret never appears in logs or the UI. Rotating means changing the Secret and
re-running the Job (delete the old row by description).

**Round 6 trap (07 §6):** `consumer_secret` is `char(43)`. A 44-char test secret made `$wpdb->insert` fail
**silently**: the script printed "inserted" and no row existed. Generate exactly `ck_`/`cs_` + 40 hex, and check the
insert's return value and `$wpdb->last_error`.

Also measured: Basic auth over in-cluster HTTP works **only** with `X-Forwarded-Proto: https`. That header also
makes WordPress build **`https://` permalinks** in REST responses, which are wrong for a plain-http local site. The
MCP tool should rewrite links to the configured public base URL.

## 2. The REST endpoints behind our five tools

Base: `/wp-json/wc/v3/…`. It's also always reachable as `/?rest_route=/wc/v3/…`, which works even with plain
permalinks (§5.3). Errors are WP REST errors: `{"code": "...", "message": "...", "data": {"status": N, ...}}`.

### 2.1 `list_products` → `GET /wc/v3/products`

- Pagination (`class-wc-rest-crud-controller.php`): `page` (≥1, default 1), `per_page` (1–**100**, default **10**),
  `offset`. Response headers carry `X-WP-Total`, `X-WP-TotalPages`, and `Link` (next/prev).
- Filters (V2/V3 controllers):
  - `search`, `sku`, `slug`, `status` (`any|draft|pending|private|publish`, default any), `type`, `featured`,
    `category` (id), `tag`, `on_sale`, `min_price`/`max_price`, `stock_status`, `include`/`exclude`;
  - `orderby` (`date|id|include|title|slug|price|popularity|rating|menu_order`, default `date`), `order` (default
    `desc`);
  - V3 adds `search_sku`, `search_name_or_sku`, `include_status`/`exclude_status`, `include_types`/`exclude_types`,
    `virtual`, `downloadable`.
- Field trimming: WordPress core `_fields=id,name,sku,price,regular_price,stock_status,stock_quantity,status,permalink`
  works on any REST response. It's the cheapest way to keep tool output small (token budget, doc 05).
- Money fields (`price`, `regular_price`, `sale_price`, totals) are **strings**.

### 2.2 `create_product` → `POST /wc/v3/products`

- Schema defaults (V3 `get_item_schema`): `type: simple`, **`status: publish`**, `featured: false`,
  `catalog_visibility: visible`, `tax_status: taxable`, `stock_status: instock`, `manage_stock: false`,
  `backorders: no`, `reviews_allowed: true`.
  - **A product created with no `status` is live on the storefront immediately.** Choice: our tool could default to
    `draft` and require an explicit `publish`, which is safer and matches Urumi's "read-only first" posture.
- Useful writable fields: `name`, `regular_price` (string), `sale_price`, `description`, `short_description`, `sku`
  (must be unique → `product_invalid_sku` error), `categories: [{id}]`, `manage_stock` + `stock_quantity`, `virtual`,
  `status`.
- **`images: [{src: "https://…"}]` makes WordPress download the URL server-side** (`wc_rest_upload_image_from_url`),
  i.e. SSRF from inside the store. Our tool should not expose `images`, or should restrict it to `{id}` of existing media.
- Permission: `wc_rest_check_post_permissions('product','create')` → `publish_products` capability.

### 2.3 `list_orders` → `GET /wc/v3/orders`

- `status` is an **array** in V3 (`status=processing` or `status[]=processing&status[]=on-hold`). Enum: `any`, `trash`,
  `auto-draft`, plus registered statuses without the `wc-` prefix: `pending`, `processing`, `on-hold`, `completed`,
  `cancelled`, `refunded`, `failed`, `checkout-draft`. Default `any`.
- Other filters: `customer` (user id), `product` (product id; implemented with a subquery), `after`/`before`
  (ISO 8601; **interpreted in the site timezone unless `dates_are_gmt=true`**), `modified_after`/`modified_before`,
  `created_via` (V3, e.g. `checkout`, `admin`, `rest-api`), `search`, `include`/`exclude`, `parent`, `orderby`/`order`.
  Pagination as above.
- HPOS (custom order tables) is **enabled for new shops** (`WC_Install::maybe_enable_hpos`). The REST layer handles both
  storages (`OrderUtil::custom_orders_table_usage_is_enabled()` branches).
  - **Round 6 correction (07 §6):** after a **WP-CLI** install + `wp plugin activate woocommerce`, HPOS was **off**
    (`woocommerce_custom_orders_table_enabled = no`). The bootstrap must run `wp wc hpos enable`. Under HPOS, editing
    a guest order needs `edit_others_shop_orders` (403 without it, verified).
- Permission: `read` → `read_private_shop_orders`.

### 2.4 `get_order` → `GET /wc/v3/orders/{id}`

- Missing id → 404 `woocommerce_rest_shop_order_invalid_id`. A non-order id (e.g. a subscription) is rejected on
  update with 400.
- Response highlights:
  - identity and status: `id`, `number`, `status`, `currency`;
  - totals (strings): `total`, `total_tax`, `shipping_total`, `discount_total`;
  - `customer_id` (0 = guest), `billing{…, email, phone}`, `shipping{…}`;
  - `payment_method` (`cod`), `payment_method_title`, `customer_note`;
  - `line_items[{id, name, product_id, variation_id, quantity, subtotal, total, sku, price}]`, `shipping_lines`,
    `fee_lines`, `coupon_lines`, `refunds`;
  - `needs_payment`, `needs_processing`, `is_editable`, `payment_url`;
  - dates `date_created`, `date_modified`, `date_paid`, `date_completed` and their `_gmt` twins.
- **Date format trap** (`wc_rest_prepare_date_response`): `gmdate('Y-m-d\TH:i:s', …)`, i.e. **no timezone offset and
  no `Z`**, even for the `_gmt` fields. The plain fields are site-local time. This is exactly why WooCommerce's own MCP
  `outputSchema` (`format: date-time`) failed for every call (woocommerce#64195). For us: emit `date_created_gmt + "Z"`
  as `created_at` and never declare `format: date-time` on a raw WooCommerce field.
- PII: billing/shipping blocks hold names, emails, phones and addresses. Return only what the tool promises, and never
  log it (doc 05, Never-do #16).

### 2.5 `update_order_status` → `PUT /wc/v3/orders/{id}` with `{"status": "completed"}`

What happens (`class-wc-rest-orders-controller.php::save_object`, V3):
1. `prepare_object_for_database` handles all writable props **except `status`**, which "should be done later so
   transitions have new data".
2. `calculate_coupons`, then `$order->set_status( $status, '', $manual_update )`, then `$order->save()`.
3. `set_paid: true` → `payment_complete()` (only if creating or `needs_payment()`).

Consequences:
- **No transition rules in REST.** Any registered status can be set from any status. Business rules ("members may not
  refund", "completed is final") must live in **our** tool or gateway policy (S-2 argument rules).
- Status hooks fire on save:
  - stock reduce/restore on transitions to and from `cancelled`;
  - customer emails ("Your order is complete"; `wp_mail` fails quietly in a container without SMTP, and the order still
    saves);
  - order notes.
- **`manual_update: true`** (V3) marks the change as manual, so the order note attributes it to the API user. Choice:
  send it, and also add our own note (`POST /orders/{id}/notes {note:"Status set to completed via Urumi MCP by
  user@team (audit id …)"}`), which puts provenance inside WooCommerce itself.
- Permission: `edit` → meta cap `edit_shop_order` for that order.

### 2.6 Error codes our tools should translate

| WC/WP code | HTTP | Meaning | Tool result |
|---|---|---|---|
| `woocommerce_rest_authentication_error` | 401 | bad key, wrong read/write scope, out-of-scope route | `isError`: "store credentials rejected" (and gateway marks upstream `auth_failed`) |
| `woocommerce_rest_cannot_view` / `_cannot_create` / `_cannot_edit` | 401/403 | user lacks capability | `isError`: "the store user isn't allowed to …" (proves least privilege) |
| `woocommerce_rest_shop_order_invalid_id`, `woocommerce_rest_product_invalid_id` | 404/400 | no such object | `isError`: "order 123 not found" |
| `rest_invalid_param` (`data.params`) | 400 | validation (e.g. bad status enum) | `isError` with the param messages, so the model can self-correct |
| `product_invalid_sku` | 400 | duplicate SKU | `isError` |
| network / 5xx | — | store down | `isError`: "store unavailable"; health signal |

## 3. Least-privilege store user (Urumi: "Scoped user, never an administrator account")

Capability mapping (`wc-rest-functions.php::wc_rest_check_post_permissions`):
`read → read_private_{type}s`, `create → publish_{type}s`, `edit → edit_{type}` (meta cap), `delete → delete_{type}`,
`batch → edit_others_{type}s`. The `shop_manager` role (`WC_Install::create_roles`) is broad. Beyond all product,
order and coupon caps it has `list_users`, `edit_theme_options`, `export`/`import`, `upload_files`, all post/page
editing, and `manage_woocommerce` (settings).

A dedicated role for the MCP server:

```bash
wp role create mcp_store_agent "MCP Store Agent"
wp cap add mcp_store_agent read \
  read_private_products edit_products edit_published_products edit_others_products publish_products assign_product_terms \
  read_private_shop_orders edit_shop_orders edit_others_shop_orders edit_published_shop_orders edit_private_shop_orders
wp user create mcp-agent mcp-agent@store.invalid --role=mcp_store_agent --user_pass="$(openssl rand -hex 24)"
```

No `delete_*`, no `manage_woocommerce`, no user/theme/export capabilities. **Negative tests**:
- `DELETE /wc/v3/products/{id}` with this key → 401/403;
- `GET /wp-json/wp/v2/users` → refused (`reject_out_of_scope_route`).

Experiment E5 must confirm the order meta-cap mapping under HPOS, because `edit_shop_order` for orders not owned by
the user goes through `edit_others_shop_orders`.

## 4. The official image, exactly (`docker-library/wordpress`)

| Fact | Detail | Consequence |
|---|---|---|
| Base | `php:8.4-apache` (Debian), **mod_php + mpm_prefork** | prefork default `MaxRequestWorkers 150` × up to 256 MB per worker ≫ any container limit → set it to ~10–20 in our image, or OOMKill under load |
| Users | apache image `www-data` = **uid 33**; `wordpress:cli` is **`php:8.4-alpine`, `www-data` = uid 82**, `USER www-data` | sharing a volume between them gives permission mismatches → run CLI with `runAsUser: 33`, or (better) put wp-cli into **our** WordPress image |
| Code location | image holds code in `/usr/src/wordpress`; entrypoint copies it to `/var/www/html` **only if `index.php` and `wp-includes/version.php` are absent** | a PVC on `/var/www/html` freezes the code at first boot (image upgrades won't apply) → don't persist the docroot; persist only `wp-content/uploads` |
| `VOLUME /var/www/html` | declared | in K8s irrelevant unless mounted; an emptyDir/PVC there triggers the copy each start |
| wp-config | generated from `wp-config-docker.php` if `wp-config.php` is missing and any `WORDPRESS_*` env is set | regenerated on every fresh container |
| Salts | template defaults `put your unique phrase here` are replaced by **random values at container start** unless `WORDPRESS_AUTH_KEY`…`NONCE_SALT` env vars are set | without the 8 env vars from a Secret, every restart or replica has different salts, so logged-in users get logged out and cookies break across replicas |
| `getenv_docker` | every setting supports `X_FILE` (read from file) | mount Secrets as files: `WORDPRESS_DB_PASSWORD_FILE=/run/secrets/db/password` |
| `WORDPRESS_CONFIG_EXTRA` | `eval()`ed PHP | where `WP_HOME`, `WP_SITEURL`, `DISABLE_WP_CRON`, `DISALLOW_FILE_MODS`, `WP_MEMORY_LIMIT`, `WP_ENVIRONMENT_TYPE` go |
| X-Forwarded-Proto | trusted unconditionally (see §1.2) | NetworkPolicy matters |
| mod_remoteip | `RemoteIPHeader X-Forwarded-For`, internal proxies 10/8, 172.16/12, 192.168/16, 169.254/16, 127/8 | client IPs in WC orders come from XFF when the hop is a pod IP |
| opcache | 128 MB, `revalidate_freq=2` | fine; with immutable code you could set `validate_timestamps=0` |
| PHP memory | php image default `memory_limit` = 128M (no php.ini) | WooCommerce wants 256 MB → ship `memory_limit=256M` ini + `WP_MEMORY_LIMIT` |

### 4.1 Immutable store image (matches Urumi's "read-only immutable images")

```dockerfile
FROM wordpress:7.1.3-php8.4-apache
# pinned plugin (verify a recorded sha256), wp-cli for the bootstrap Job, PHP/Apache tuning
COPY woocommerce/ /usr/src/wordpress/wp-content/plugins/woocommerce/
COPY wp-cli.phar /usr/local/bin/wp          # sha512 published by wp-cli/builds
COPY php-urumi.ini /usr/local/etc/php/conf.d/  # memory_limit=256M, upload limits
COPY mpm_prefork.conf /etc/apache2/mods-available/
```

In the Deployment, code comes from the image. Don't mount `/var/www/html` at all; the entrypoint copies
`/usr/src/wordpress` into the container's own writable layer on start. Mount a PVC only at `wp-content/uploads`, and
set `DISALLOW_FILE_MODS` so nobody installs plugins at runtime. The bootstrap Job uses **the same image** with
`command: ["wp", …]`: same uid 33, same files, same plugin version.

## 5. Bootstrapping a working store (Job, idempotent)

### 5.1 The sequence

```bash
set -euo pipefail
wp core is-installed || wp core install --url="$WP_HOME" --title="Urumi Demo Store" \
   --admin_user="$ADMIN_USER" --admin_password="$ADMIN_PASS" --admin_email="$ADMIN_EMAIL" --skip-email
wp plugin is-active woocommerce || wp plugin activate woocommerce
wp rewrite structure '/%postname%/'                   # §5.3
wp option update woocommerce_coming_soon no            # §5.2
wp option update woocommerce_default_country "IN:KA"   # store base (affects tax/shipping/checkout fields)
wp option update woocommerce_currency INR
wp option update woocommerce_onboarding_profile '{"skipped":true}' --format=json
wp wc payment_gateway update cod --enabled=true --user="$ADMIN_USER"      # COD defaults to disabled
wp wc shipping_zone_method create 0 --method_id=free_shipping --user="$ADMIN_USER"  # zone 0 = "rest of world"
# products: wp wc product create --name=… --regular_price=… --user=… (skip if SKU exists)
# role + user + key: §3 and §1.3
```

Each step is check-then-act so a re-run (e.g. a Helm upgrade) is harmless. The previous hiring cycle's best
submission had an idempotent seeder too (doc 05).

### 5.2 Coming-soon mode

`WC_Install::add_coming_soon_option()` (hooked on `woocommerce_newly_installed`) does
`add_option('woocommerce_coming_soon','yes')` and `add_option('woocommerce_store_pages_only','yes')`. A fresh store
shows a "coming soon" page to logged-out visitors on store pages, so **the DoD storefront checkout fails until
`woocommerce_coming_soon = no`**. Also, `is_new_install()` (11.0+) treats `coming_soon = no` as "store is live".

Round 6 (07 §6): right after `wp plugin activate woocommerce` the option was **unset**. The hook adds `yes` later,
so setting `no` explicitly in the bootstrap (before any page load) is what keeps the store live.

Other measured bootstrap facts:
- the site timezone defaults to UTC (`timezone_string=''`), so set it;
- `sendmail` is absent, so WooCommerce writes "Email … failed to send" order notes;
- a guest COD checkout through the Store API (`/wc/store/v1/cart` → `add-item` → `checkout`, with `Cart-Token` and
  `Nonce` headers) yields `processing`.

### 5.3 Permalinks

`wp core install` → `wp_install_maybe_enable_pretty_permalinks()`. This only enables
`/%year%/%monthnum%/%day%/%postname%/` if a **loopback HTTP request** to the first post succeeds. From a Job pod that
loopback usually fails (the site URL isn't routable from there), so permalinks stay plain. With plain permalinks
`/wp-json/…` isn't routed and only `/?rest_route=…` works. Fix: `wp rewrite structure '/%postname%/'` (the image ships
the standard `.htaccess`). Our MCP server can use `?rest_route=` anyway, which works in both cases.

### 5.4 Checkout path for the DoD

- Cart and Checkout pages are created at install with **block** content (`WC_Install::create_pages`, the shortcode
  filters are deprecated since 8.3). Checkout goes through the Store API (`/wc/store/v1/checkout`).
- COD gateway (`includes/gateways/cod/class-wc-gateway-cod.php`):
  - `enabled` defaults to `no`; `enable_for_methods` empty means all shipping methods; `enable_for_virtual` defaults to
    `yes`.
  - `is_available()` checks virtual carts and shipping methods.
  - `process_payment` sets status **`processing`** (or `on-hold` if the order has downloadable items), via
    `woocommerce_cod_process_payment_order_status`.
- Shipping: physical products with no matching zone method → "no shipping options" at checkout. Fix: a free-shipping
  method on zone 0 (above), virtual products, or `woocommerce_ship_to_countries = disabled`.
- Guest checkout is on by default (`woocommerce_enable_guest_checkout = yes`).
- So the demo: buyer checks out with COD → order `processing` → chat agent `list_orders(status=processing)` →
  `update_order_status(id, completed)`.

### 5.5 Hostnames per environment

WordPress stores absolute URLs (`home`, `siteurl` options; links in content). Define `WP_HOME`/`WP_SITEURL` in
`WORDPRESS_CONFIG_EXTRA` from Helm values (`http://store.localtest.me:8080` locally, `https://store.<domain>` on the
VPS). The constants override the DB options, so moving environments needs no `search-replace`. In-cluster REST calls
with a different `Host` header are fine: REST is dispatched at `parse_request`, before `redirect_canonical` (front-end
only) would redirect.

### 5.6 Background work

- WP-Cron runs on page loads by default. `DISABLE_WP_CRON` plus a CronJob (`wp cron event run --due-now`, same image)
  is the K8s way.
- WooCommerce's Action Scheduler also uses async loopback requests to `admin-ajax.php` on the site URL. These fail when
  the site URL isn't reachable from inside the pod (Site Health "loopback request failed").
  - Mitigation: a CronJob running `wp action-scheduler run`.
  - Basic order and product REST calls don't depend on it; emails and analytics do.

## 6. Database choice facts

- WooCommerce recommends MySQL ≥ 8.0 or **MariaDB ≥ 10.6**; MariaDB 11.4 LTS qualifies.
- Required SQL modes listed by WooCommerce (optional strictness): `ERROR_FOR_DIVISION_BY_ZERO`,
  `NO_ENGINE_SUBSTITUTION`, `NO_ZERO_DATE`, `NO_ZERO_IN_DATE`, `STRICT_ALL_TABLES`.
- MySQL 8.4 disables `mysql_native_password` by default, and its initialiser refuses a non-empty datadir (`lost+found`
  on some volumes); see doc 05. k3s `local-path` volumes are plain host directories (no `lost+found`).

## 7. What our WooCommerce MCP server should look like (derived, for the decision chat)

- 5 tools, small explicit schemas, `additionalProperties: false`.
  - `list_products(search?, status?, page?, per_page≤50)`
  - `create_product(name, regular_price, sku?, description?, status=draft|publish, stock_quantity?)`
  - `list_orders(status?[], after?, page?, per_page≤50)`
  - `get_order(order_id)`
  - `update_order_status(order_id, status ∈ allowed set, note?)`
- `annotations`: list/get `readOnlyHint: true`; create `destructiveHint: false`; update `destructiveHint: true`,
  `idempotentHint: true`.
- Outputs: a compact text summary **plus** `structuredContent`. Declare an `outputSchema` only for fields we normalise
  ourselves (ISO dates with `Z`, numbers as strings or decimals), and contract-test it (05 Never-do #13).
- Use `_fields` on every REST call; map WC errors per §2.6; add an order note on status changes; never log
  billing/shipping data.
- Calls go `http://wordpress.<ns>.svc/?rest_route=/wc/v3/...` with `Authorization: Basic base64(ck:cs)` and
  `X-Forwarded-Proto: https`, a per-request timeout (e.g. 8 s), and connection keep-alive.
